# 独立 Linux Node Agent（节点代理）部署交付物

## 状态与边界

本目录提供的是可审查的部署资料，不是已完成部署的声明。截至本提交：

- 已实现：专用 `systemd（系统服务）` 单元、受限环境模板、启动前检查、认证健康/容量验证脚本及静态测试。
- 已验证：资料的静态安全约束与 Python（解释器）测试；不会在本机安装服务、读取实际令牌或连接远程节点。
- 未运行：真实 Linux（操作系统）主机上的安装、`systemd（系统服务）` 启动、远程私网连通、TLS（传输层加密）代理、真实浏览器终端尺寸变化和生产验收。

它只服务于独立 Linux（操作系统）计算节点；控制面仍通过已认证的 Node Agent（节点代理）调用受控 RPC（远程过程调用），浏览器和 Control API（控制面接口）均不直接接触 Docker Socket（容器运行接口）。

## 安全模型

- 服务默认监听 `127.0.0.1`；如必须跨主机，仅可改为私有 IP（地址），并经已审查的私网 TLS（传输层加密）反向代理或等价受限通道接入。绝不将端口直接暴露公网。
- Node Agent（节点代理）是唯一被允许调用本机 Docker CLI（容器命令行）的宿主机进程。它不是容器，因而不使用 Docker Socket（容器运行接口）挂载；绝不为方便运行把它包进带 socket mount（套接字挂载）的容器。
- `docker` 组通常等同于宿主机高权限边界。专用 `yueke-agent` 账户只能用于本服务，代码发布目录与配置目录必须分别由受控发布账户、`root`（超级用户）持有；不要向普通教师、学生或 Web 进程授予该组。
- 单元要求非 root（非超级用户）账户、`NoNewPrivileges`（禁止新增权限）、只读系统目录、私有临时目录、禁用额外 capability（Linux 能力）、受限地址族和受控状态目录。实验容器本身仍由 `node_agent/app.py` 继续强制禁止 privileged（特权）、host network（宿主网络）、host PID/IPC（宿主进程/进程间通信）和 bind mount（宿主目录挂载）。
- 环境文件只允许本项目必需字段；启动前检查拒绝远程 Docker context（上下文）、公网监听、未固定镜像摘要、过宽权限、符号链接配置和不安全抓包目录。脚本不会输出令牌或配置值。

## 文件

| 文件 | 用途 |
| --- | --- |
| `yueke-node-agent.service` | 最小权限 systemd（系统服务）单元；默认单 worker（单工作进程），避免运行组内存锁被复制。 |
| `node-agent.env.example` | 不含真实秘密的环境模板；故意不能直接通过检查。 |
| `preflight.sh` | 安装/启动前只读校验 Linux（操作系统）、本机 Docker Engine（容器引擎）、固定摘要、目录和配置权限。 |
| `verify-service.sh` | 以令牌在进程内发送健康与容量请求；不将令牌写入命令行或输出。 |

## 实施人员使用：受控安装流程

以下步骤只供获得目标 Linux（操作系统）节点变更授权的实施人员执行；本仓库的自动化不会执行它们。执行前先记录目标主机、现有服务、端口、Docker context（上下文）、代码版本与可恢复保护点。不要在生产数据库、业务 Web 服务或其他系统目录中执行。

1. 在独立节点创建专用、不可登录的服务账户，并仅把它加入本机 Docker `docker` 组；确认该账户不属于其他业务服务组。
2. 将候选版本放入独立发行目录，例如 `/opt/yueke-node-agent/releases/<已验证提交>`，完成依赖安装和代码校验后，再把 `/opt/yueke-node-agent/current` 原子切换到该候选目录。`/opt/yueke-node-agent`、`releases`、候选目录、解释器和部署脚本都必须由 `root`（超级用户）持有，且不得允许组或其他用户改写；不得直接覆盖正在运行的目录。
3. 从 `node-agent.env.example` 创建 `/etc/yueke-node-agent/node-agent.env`，只在受限路径填入真实随机令牌、审核后的固定镜像摘要和私有监听地址。令牌、密码和私有地址不得进入仓库、聊天记录、日志或截图。配置文件应为 `root:yueke-agent`、`0640`；抓包目录应为 `/var/lib/yueke-node-agent/captures`，由服务状态目录创建。
4. 先以 `yueke-agent` 账户运行 `preflight.sh`；它只读取配置、Docker 信息和应用导入，失败时不创建容器或网络。检查通过后，才由有授权的实施人员安装单元、执行 `daemon-reload` 并启动服务。
5. 本机用 `verify-service.sh` 验证受认证的 `/health` 与 `/capacity`。若通过私网代理远程验证，第二参数必须是 `https://` 地址；脚本拒绝把令牌发送到远程明文 HTTP（超文本传输协议）。
6. 之后再运行现有 Linux Docker（容器引擎）Gate（门禁）和浏览器 Gate（门禁）；服务健康不等于 G4/G5/G6（实验运行、浏览器终端、自动判分）通过。

## 回退

Node Agent（节点代理）不拥有正式 MySQL（数据库）迁移。本服务升级失败时：停止后续切换，保留日志和当前发行目录；将 `current` 原子指回上一个已验证发行目录；先重新运行该版本的 `preflight.sh`，再重启服务并用 `verify-service.sh` 复核。不要删除 `/var/lib/yueke-node-agent` 中仍需导出的抓包证据，也不要为了回退执行 Docker 数据清空或数据库回退。若新旧控制面契约不兼容，先停止并由总控确认兼容版本，而不是盲目降级。

## 验收清单

1. `systemd（系统服务）` 显示服务由 `yueke-agent` 运行，未以 root（超级用户）运行。
2. `preflight.sh` 显示 Linux Docker Engine（容器引擎）与本机 Unix socket（套接字）上下文均合格。
3. `verify-service.sh` 返回已认证的健康与容量摘要，且不泄露令牌。
4. 防火墙、私网路由或 TLS（传输层加密）代理证明控制面可达、普通终端和公网不可达。
5. 独立 Linux Node Agent（节点代理）上运行 G4、G5、G6 门禁，特别记录 POSIX/PTTY（伪终端）尺寸从 `24x80` 变为 `30x100` 的真实证据。
